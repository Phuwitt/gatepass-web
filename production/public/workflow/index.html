ส่วนสถานะความหมาย

02 · ระบบนี้ทำอะไร

ระบบจัดการสิทธิ์เข้า–ออกและข้อมูลเวลางานขององค์กรเดียว พนักงานยืนยันตัวตนที่เครื่องประตู ผู้ดูแลจัดการผ่านเว็บ

  1. Admin ตั้งค่าพื้นที่ ประตู เครื่อง และบัญชี HR
  2. HR เพิ่มพนักงาน ลงทะเบียนข้อมูลยืนยันตัวตน และกำหนดสิทธิ์ประตู/เวลา
  3. พนักงานใช้ใบหน้า บัตร หรือ QR ตามวิธีที่ได้รับอนุญาต ไม่จำเป็นต้องใช้ทุกวิธีร่วมกัน
  4. Backend ตรวจตัวตนและสิทธิ์ บันทึกผลอนุญาต/ปฏิเสธพร้อมเหตุผล
  5. HR ตรวจเวลางาน การลา และคำขอแก้เวลา โดยไม่แก้ทับ raw event

NFC มือถือ HCE เป็นคนละส่วนกับบัตร NFC จริง ต้องมีแอป HCE เพิ่ม ยังไม่ได้สร้างแอปนั้นในรอบนี้

ระบบนี้ไม่ใช้ ThingsBoard หรือ Edge Impulse เป็นระบบล็อกอินหรือฐานข้อมูลหลัก

03 · ภาพรวมว่าอะไรเชื่อมอะไร

เว็บเป็นหน้าจอใช้งาน Backend เป็นผู้ตัดสินสิทธิ์ และ Supabase เก็บข้อมูล ส่วนบอร์ดรับภาพ/บัตรและส่งคำขอ ไม่ถือ service key ของ Supabase

01Admin / HR / พนักงาน
02เว็บใน Browser
03Next.js API บน Mac
04Supabase Auth + PostgreSQL + private Storage
  1. Browser กับ Next.js ใช้ origin เดียวกัน เช่น http://localhost:3000
  2. บอร์ดต่อ Wi-Fi แล้วเรียก IP LAN ของ Mac เช่น http://192.168.1.20:3000 ไม่ใช้ localhost ของบอร์ด
  3. เมื่อส่งหน้า Next.js ส่ง JPEG ต่อไป Face Service บน 127.0.0.1:8001
  4. Face Service ใช้ YuNet ตรวจตำแหน่งใบหน้าและ SFace สร้างเวกเตอร์ 128 ค่า
  5. Backend เปรียบเทียบเวกเตอร์กับ template และอ่านสิทธิ์จาก PostgreSQL
  6. Cloud เปลี่ยนเฉพาะปลายทางฐานข้อมูล เว็บและบริการใบหน้ายังอยู่ Mac จนกว่าจะย้ายโฮสติ้ง

ช่องทางเครื่องเป็น HTTP API ใน LAN สำหรับทดสอบ ยังไม่ได้ใช้ MQTT

Cloud ของ Supabase ไม่ได้ทำให้เว็บ localhost เปิดจากนอกบ้านได้เอง

04 · บัญชีและหน้าที่

ใช้ Supabase Auth ยืนยันบัญชี แล้วตรวจ gp_profiles และสถานะพนักงานใน Backend ทุกครั้ง ไม่เชื่อ role ที่ส่งจากหน้าจอ

ผู้ใช้ทำอะไรขอบเขต
Adminจัดการระบบและสร้าง HR/บัญชีพนักงานสิทธิ์ระบบสูงสุด
HRพนักงาน บัตร ใบหน้า สิทธิ์ประตู เวลางาน การลาไม่มีสิทธิ์สร้าง Admin ผ่านงาน HR
Employeeดูข้อมูลตนเอง ส่งคำขอลา/แก้เวลา และยืนยัน QRเข้า Admin/HR API ไม่ได้
Deviceheartbeat / JPEG / UID / QR-sessionใช้ device token แยกจากบัญชีคน ไม่มี database key

05 · เตรียมเครื่องและของ

ช่วงซอฟต์แวร์ใช้ Mac ที่มี Node.js, Python และไฟล์โมเดล; การทดสอบจริงต้องตรวจรุ่นอุปกรณ์ที่ซื้อให้ตรงก่อนต่อ

  1. Node dependency ใช้ package-lock.json และ npm ci เมื่อต้องติดตั้งใหม่
  2. Face Service อยู่ face-service/.venv มี requirements.lock.txt และโมเดลที่ตรวจ SHA-256
  3. Docker จำเป็นเฉพาะเมื่อใช้ Supabase local; ถ้าเปลี่ยนไป Cloud จริงแล้ว ไม่ต้องเปิดฐานข้อมูล local สำหรับเว็บนั้น
  4. กล้องเก่าที่ตรวจโค้ดไว้เป็น AI Thinker ESP32-CAM; PCB ใหม่ต้องตรวจรุ่น MCU, PSRAM, กล้อง และ pin map แยก
  5. ตัวอย่าง reader ใช้ PN532 SPI กับ ESP32-S3 DevKit อ่านบัตร ISO14443A ที่รองรับ ไม่ใช่ RFID 125 kHz
  6. เตรียมไฟเลี้ยงและสาย USB ที่ถูกต้อง ไม่ใช้ผล heartbeat แทนการวัดแรงดันหรือยืนยันว่ากล้องทำงาน

06 · เปิดระบบ local ตั้งแต่ศูนย์

โฟลเดอร์งานคือ gatepass-web-v2 เก็บเว็บเก่า gatepass-web แยกไว้และไม่ลบฐานข้อมูลเดิม

  1. เปิด Terminal ที่ /Users/phuwit/Documents/Allproject/CPE_3_Project/gatepass-web-v2
  2. รัน npm run local:start: ตรวจพอร์ต 3000/8001 → เปิดฐานข้อมูลเดิมถ้าใช้ local → เปิด Face Service → เปิดเว็บ
  3. เปิด http://localhost:3000 ใช้บัญชีเดิมของ local; ไม่มีการตั้งรหัสผ่านเริ่มต้นใหม่
  4. หากใช้บอร์ดจริง ให้หยุดบริการที่ใช้พอร์ตเดิมก่อน แล้วเปิด npm run local:lan เพื่อรับจาก LAN
  5. เปิด /api/v1/health ตรวจ database และ face_service ต้อง true
  6. ครั้งแรกของฐานข้อมูลใหม่ ใช้ลิงก์ setup ส่วนตัวใน .local-access.txt แล้วผู้ใช้เป็นคนกำหนดรหัสผ่านเอง

ห้ามรัน db reset, docker prune หรือ stop --no-backup เพื่อแก้ปัญหาเข้าไม่ได้

local:start จะไม่เลือกพอร์ต 3001 เงียบ ๆ ถ้าพอร์ตเดิมไม่ว่าง ให้หยุด process ของเว็บก่อน

07 · เปลี่ยนไป Supabase Cloud จริง

สร้าง project ฟรีชื่อ gatepass ใน Organization GATEPASS แล้ว โดยได้รับราคา $0 จากเครื่องมือก่อนสร้าง ไม่มีการอัปเกรดแพ็กเกจ โฮสติ้งยังรอไว้

  1. Dashboard: https://supabase.com/dashboard/project/exzqwzkagzhdcuyvcsoz
  2. schema, RLS, private bucket และฟังก์ชันธุรกรรมถูกติดตั้งแล้ว
  3. จุดที่ยังค้าง: เครื่องมือ MCP ให้จัดการ SQL ได้ แต่ไม่คืน secret/service_role key; CLI และ Dashboard ยังไม่ยืนยันบัญชีในเครื่อง
  4. ล็อกอิน Dashboard ของบัญชีที่เป็นสมาชิก Organization แล้วเปิด Settings → API Keys
  5. บน Mac รัน npm run cloud:configure แล้ววาง publishable/anon key และ secret/service_role key ลง Terminal ที่ไม่แสดงตัวอักษร ไม่ส่ง key ในแชต
  6. สคริปต์ตรวจอ่าน gp_setup บน Cloud ก่อน ถ้าไม่ผ่านจะไม่แก้ config; ถ้าผ่านจะสำรอง .env.local และเขียนไฟล์สิทธิ์ 0600
  7. หยุด/เริ่มเว็บใหม่ ตรวจ health.database_target เป็น cloud และ database=true
  8. Cloud เริ่มด้วยข้อมูลว่าง บัญชีและข้อมูล local ไม่ได้ถูกย้ายอัตโนมัติ ให้สร้าง Admin Cloud ผ่าน private setup link
  9. ก่อนย้ายข้อมูลจริง ให้ทำ backup และแผนจับคู่ auth_user_id ใหม่ ห้ามคัดลอก password หรือ hash แบบสุ่มไปทับ Cloud

ขณะจัดทำคู่มือนี้เว็บยังเชื่อม local จึงไม่อ้างว่าผู้ใช้กำลังอ่าน/เขียน Cloud แล้ว

ใช้บริการฟรีตาม quota ปัจจุบัน ไม่เปิดส่วนเสียเงิน; ราคา/โควตาอาจเปลี่ยนได้ ให้ตรวจ Dashboard ก่อนใช้งานจำนวนมาก

เมื่อ Cloud พร้อมแล้ว local:start จะข้ามการเปิด Docker; Mac ยังต้องรัน API และ Face Service

08 · Workflow ล็อกอิน

ทุกคนใช้หน้าเข้าเดียวกันแล้วระบบแยกพื้นที่ทำงานตามบทบาท

01กรอกอีเมล/รหัสผ่าน
02POST /api/auth/login

04Backend ตรวจ gp_profiles.active + role

  2. session cookie ใช้ httpOnly และ sameSite=lax; APP_HTTPS=true เมื่อใช้งานผ่าน HTTPS จริง
  3. การเปลี่ยนวิธีหรือสิทธิ์ต้อง POST จาก origin เดียวกับเว็บ
  4. บัญชีไม่มี profile หรือถูกระงับจะถูกปฏิเสธ แม้ Auth login ได้

09 · เพิ่มพนักงานและข้อมูลประจำตัว

หนึ่งคนใช้ employee_id คงที่ แล้วเชื่อมใบหน้า บัตร สิทธิ์ และประวัติผ่านค่านี้

  1. พนักงาน → เพิ่มพนักงาน: รหัสไม่ซ้ำ ชื่อ แผนก และอีเมล
  2. ดูรายละเอียด → ตั้งเวลางาน work_start/work_end และ grace_minutes
  3. สร้างบัญชี Employee เฉพาะคนที่ต้องใช้ portal/QR โดย Admin เป็นผู้สร้าง
  4. กำหนด active=true เฉพาะคนที่ใช้งาน; ระงับบัญชีเมื่อออกจากงาน
  5. เปิด face_enabled หรือวิธี card/nfc/qr ตามขอบเขตที่ต้องใช้
  6. เพิ่มข้อมูลยืนยันและสิทธิ์ประตูแยกกัน การสร้างพนักงานอย่างเดียวยังเข้าไม่ได้

รหัสพนักงานใช้ A–Z a–z 0–9 _ - ยาว 1–40 ตัว

local และ Cloud เป็นคนละฐานข้อมูล การเห็นชื่อใน local ไม่ได้แปลว่ามีบน Cloud แล้ว

10 · โซน ประตู เครื่อง และทิศทาง

โครงสร้างสถานที่ใช้ zone → door → device โดยเครื่องประตูผูกกับประตูที่ถูกต้องก่อนรับเหตุการณ์

01เพิ่มโซน

03เพิ่ม Device ID และผูกประตู

05ตั้งค่าเครื่อง

  1. สร้างโซน เช่น อาคารสำนักงาน แล้วประตู เช่น ทางเข้าอาคาร
  2. สร้างเครื่องด้วย Device ID ตรงกับ firmware; ปัจจุบันหนึ่งเครื่อง active ต่อหนึ่งประตู
  3. รหัสลงทะเบียนอายุ 30 นาที แสดงครั้งเดียว ต้องคัดลอกไปตั้งค่าเครื่อง
  4. กำหนด direction เป็น in หรือ out เพื่อคำนวณเวลางาน; ถ้าไม่ทราบให้ unspecified
  5. การเปลี่ยน direction มีผลกับ event ใหม่ ไม่แก้ event เก่าย้อนหลัง
  6. ออกโค้ดใหม่จะยกเลิก credential เดิมของเครื่อง ต้องยืนยันก่อน; เพิกถอนเครื่องเมื่อหาย

11 · ลงทะเบียนเครื่องและ heartbeat

รหัสลงทะเบียนถูกแลกเป็น device token ครั้งเดียว Backend เก็บเฉพาะ hash และบอร์ดเก็บ token ใน NVS

01บอร์ดต่อ Wi-Fi
02POST /api/device/enroll
03ตรวจรหัส/วันหมดอายุ/การใช้ซ้ำ
04คืน device token หนึ่งครั้ง
05บอร์ดเก็บ NVS
06heartbeat พร้อม Bearer token
  1. เรียกหลังลงทะเบียนทุกครั้งต้องมี X-Device-ID และ Authorization: Bearer <device_token>
  2. heartbeat ส่ง firmware, RSSI, camera_ready, card_reader_ready และ sensor ที่วัดจริงเท่านั้น
  3. สถานะติดต่อ: ต่ำกว่า 25 วินาที Online, 25–44 วินาที Stale, ตั้งแต่ 45 วินาที Offline; เวลาอนาคตผิดปกติเป็น Unknown
  4. Online ไม่รับรองว่าไฟยังอยู่ทันที เป็นเพียงได้รับ heartbeat ล่าสุด
  5. กล้องและ reader แสดงตามรายงานเฟิร์มแวร์แยกจากการติดต่อ; ค่าเดิมที่ไม่ส่งเป็นยังไม่รายงาน
  6. เฟิร์มแวร์ใหม่ส่ง heartbeat ประมาณ 3 วินาทีเพื่อให้คำสั่งรอแตะบัตรถึงเร็ว

12 · ตั้ง Wi-Fi และอัปโหลด

เฟิร์มแวร์มี provisioning เดิมสำหรับใส่ Wi-Fi และค่าเครื่องผ่าน AP ของบอร์ด

  1. เปิด .ino หรือ PlatformIO environment ที่ตรงกับบอร์ด; อย่าใช้ g++ รัน .ino โดยตรง
  2. Monitor 115200; ปิด monitor ก่อน Upload เพื่อคืน serial port
  3. บอร์ดไม่มีค่าตั้ง/ต่อ Wi-Fi ไม่ได้จะเปิด GATEPASS-SETUP ชื่อและรหัสแสดงใน Serial แล้วเข้า 192.168.4.1
  4. กรอก Wi-Fi ของสถานที่, API URL เป็น IP LAN ของ Mac, Device ID และรหัสลงทะเบียนจากเว็บ
  5. Mac และบอร์ดต้องอยู่เครือข่ายที่ติดต่อกันได้ ไม่มี client isolation; ใช้ Wi-Fi 2.4GHz ตามบอร์ด
  6. คำสั่ง W เปิดหน้าตั้งค่า; R ล้าง device credential แล้วตั้งใหม่ อย่ากด R โดยไม่มีรหัสลงทะเบียนใหม่
  7. HTTP อนุญาตเฉพาะ IP LAN ในโหมดทดสอบ; HTTPS ต้องมี root CA และเวลาถูกต้อง ไม่ใช้ setInsecure

  2. JPEG ไม่เกิน 2 MB และจำกัดจำนวนพิกเซล; ภาพเสีย/ไม่พบหน้า/หลายหน้าจะถูกปฏิเสธ

  1. เปรียบเทียบ SFace vector ใช้ threshold เริ่ม 0.45 และคะแนนห่างอันดับสองอย่างน้อย 0.04
  2. ตรวจพนักงาน active, face_enabled, template ปัจจุบัน และ permission ของประตู

  4. ถ้าส่งซ้ำใช้ request_id และภาพเดิม ป้องกัน event ซ้ำ; เปลี่ยน payload ด้วย request_id เดิมถูกปฏิเสธ

  6. ผลยังไม่สั่งกลอนและไม่มี liveness จึงยังไม่ใช้เป็นข้อยืนยันว่าป้องกันภาพถ่ายได้

15 · ผูกบัตร RFID / NFC กับพนักงาน

เพิ่มหน้าและ API รอแตะบัตรจริงไว้แล้ว ใช้ UID ของบัตรที่ reader รองรับและผูกกับ employee_id ที่เลือก ไม่ใช้ชื่อที่ส่งจากบอร์ด

01พนักงาน → ดูรายละเอียด
02เลือกเครื่องอ่านและชื่อบัตร
03เริ่มรายการ 2 นาที
04heartbeat รับ session ID
05แตะบัตร → card-capture
06ตรวจบัตรซ้ำ / เครื่อง / อายุ
07เว็บเห็นเลขท้าย
08ยืนยันผูกบัตร
  1. เครื่องต้องติดต่อภายใน 45 วินาทีและรายงาน card_reader_ready=true; กล้องอย่างเดียวเริ่มรายการไม่ได้
  2. หนึ่งเครื่องรับรายการค้างได้เพียงหนึ่งรายการ ป้องกันผู้ดูแลสองคนใช้ reader พร้อมกันคนละคน
  3. session กำหนด employee_id,device_id,created_by,label ตายตัวตั้งแต่เริ่ม
  4. บอร์ดส่ง session UUID + UID ผ่าน credential เครื่อง; UID ยาว 4, 7 หรือ 10 ไบต์ normalize hex
  5. บัตรที่ hash มีอยู่แล้ว แม้บัตรเดิมถูก revoke ก็ไม่ผูกทับอัตโนมัติ ต้องให้ผู้ดูแลตรวจเจ้าของก่อน
  6. ก่อนยืนยันเก็บเพียง hash และ last_four ใน session ไม่สร้าง credential หรือ access event
  7. เฉพาะผู้ดูแลที่เริ่มรายการกดยืนยันได้ ตรวจ profile/employee/device active อีกครั้งใน transaction
  8. ยืนยันพร้อมกันหรือกดย้ำสร้าง credential เดียว และ audit เดียว
  9. การผูกบัตรไม่เปิดวิธี card และไม่เพิ่มสิทธิ์ประตูเอง
  10. กดยกเลิก หรือรอหมดอายุแล้วเริ่มใหม่ได้; ออกจากหน้าจะทิ้ง session ให้หมดอายุใน 2 นาที

กรอก UID ด้วยมือยังมีเป็นทางเลือก แต่แนะนำใช้รอแตะเพื่อเลี่ยงพิมพ์ผิด

Backend เก็บ hash ไม่ได้ทำให้ UID ของบัตรป้องกันการ clone ได้

ถ้ากดเริ่มแล้ว reader ยังอ่านไม่ขึ้น ให้ตรวจ interface/โหมด/รุ่น ไม่ใช้ serial พิมพ์ UID แล้วอ้างว่า hardware ผ่าน

16 · ใช้บัตรและเปลี่ยนบัตรหาย

หลังผูกข้อมูลแล้ว ต้องเปิดวิธีและ permission ก่อนแตะเพื่อเข้าได้

  1. HR เปิดวิธี card ของคนนี้ และเพิ่มสิทธิ์ประตูที่ใช้งาน
  2. บอร์ดต้องไม่อยู่ในโหมด enrollment เมื่อใช้บัตรเข้าประตู
  3. บัตรถูก revoke / ไม่มีคน / คนถูกระงับ / วิธีปิด / ไม่มี permission / นอกเวลา ต้องปฏิเสธ
  4. บัตรหายให้ revoke บัตรเก่าจากรายละเอียดพนักงาน ประวัติเดิมไม่ถูกลบ
  5. เพิ่มบัตรใหม่ของคนเดิมแล้วทดสอบวิธีบัตรอีกครั้ง ไม่เปลี่ยน employee_id
  6. UID เดิมที่อยู่คนอื่นต้องไม่สามารถย้ายเจ้าของด้วยการยืนยันผูกใบใหม่ได้

17 · NFC มือถือไม่ใช่บัตรทั่วไป

ระบบเตรียม API สำหรับ credential มือถือแยกจาก UID ของบัตรจริง การอ่าน UID ของมือถือไม่ใช่วิธีระบุพนักงานที่เชื่อถือได้

  1. HR สร้าง credential แบบ nfc ได้ค่าสุ่ม 64 hex แสดงครั้งเดียวและเก็บเฉพาะ hash
  2. ต้องมีแอป Android HCE ที่รับ credential อย่างปลอดภัยและส่งผ่าน APDU ที่ reader รองรับ
  3. ต้องกำหนด AID, APDU, challenge/replay protection และการจัดเก็บคีย์ในมือถือก่อนใช้จริง
  4. เว็บอย่างเดียวไม่ทำให้มือถือกลายเป็นบัตร และไม่ได้ยืนยันการรองรับ iPhone
  5. ในรอบนี้ทดสอบ endpoint และ grant เท่านั้น ยังไม่ได้สร้าง/ทดสอบแอป HCE หรือ APDU จริง

  5. QR TTL ยังไม่ได้รับรองว่าอยู่หน้าประตูจริง หากต้องการป้องกันส่งรูปต่อ ต้องเพิ่มกลไกด้าน proximity/การกำกับใช้งาน

  5. สายเทียบ work_start + grace_minutes ตามวันเวลาไทย
  6. พนักงานส่งคำขอลา; HR พิจารณาอนุมัติ/ปฏิเสธ
  7. คำขอแก้เวลาบันทึกเหตุผลและผู้อนุมัติ แก้เฉพาะรายงาน ไม่เขียนทับ raw event
  8. หน้า history สูงสุด 200 รายการล่าสุด; HR ตามเดือนมีขอบเขตโหลด อย่าอ้างว่าเป็นคลังประวัติไม่จำกัด
  9. ยังไม่รองรับกะข้ามคืน และไม่หักพักอัตโนมัติ

24 · ดูกล้องทางเข้า

ดู JPEG จากบอร์ดผ่าน Backend ไม่ใช่ภาพจากกล้อง Mac และไม่ใช่ CCTV 24 ชั่วโมง

  1. เลือกเครื่องที่ถูกและกดเริ่มดูภาพ; หยุดเมื่อไม่ใช้เพื่อลดการส่งภาพ
  2. preview ใช้ memory cache ของ API process ไม่เก็บเป็นวิดีโอถาวร
  3. กล้อง error แม้ heartbeat200 ก็ยังไม่มีภาพ ต้องตรวจกล้องแยก

  5. ยังไม่ได้วัดกำลังไฟ/ความร้อนจริงจากบอร์ด จึงไม่ระบุว่าเปิด24ชม.ปลอดภัยจากโค้ดอย่างเดียว

26 · สิทธิ์ข้อมูลและความปลอดภัย

Browser/บอร์ดไม่รับ Supabase service key ทุกตาราง public เปิด RLS และตาราง secret ไม่มี policy ฝั่ง client โดยตั้งใจ

  1. ตาราง credential,device secret,face vector,QR secret,setup,card session ถูก revoke จาก anon/authenticated
  2. Backend ใช้ service key จึงต้องตรวจ role/owner/device token ทุก endpoint ไม่พึ่ง RLS อย่างเดียว
  3. helper gp_is_manager เปลี่ยนเป็น security invoker และห้าม anon execute
  4. function capture/confirm ใช้ transaction และ row lock และให้ execute เฉพาะ service_role
  5. ค่าคีย์และ .local-access.txt มีสิทธิ์ไฟล์0600 และอยู่ใน .gitignore
  6. advisors Cloud หลังแก้ไม่มี WARN เหลือ INFO ว่าตาราง privateไม่มี policy ซึ่งเป็นการปิด client accessตามเจตนา
  7. หน้า public workflow ไม่มีคีย์ รหัสผ่าน หรือข้อมูลชีวมิติ
  8. ก่อน production ต้องมี HTTPS, rate limit ที่รองรับหลาย process, retention, backup/restore, monitoring และทบทวนสิทธิ์จริงอีกครั้ง

ไม่มี liveness และยังไม่รับรองป้องกัน clone/replay ในทุกช่องทาง

API serverเป็นจุดตัดสิน ไม่ควรเปิดพอร์ตออก Internet ก่อนตรวจระบบพร้อม

27 · วิธีทดสอบและหลักฐาน

Automated test ใช้ฐานข้อมูล local เท่านั้น สร้าง QA ชั่วคราวและล้างเฉพาะข้อมูล QA ไม่ใช้บัญชีผู้ใช้เป็น fixture

  2. npm run typecheck และ npm run build ตรวจเว็บ
  3. node tests/api-integration.mjs ตรวจ Browser API → Supabase Auth → PostgreSQL/Storage → response
  4. ทดสอบสิทธิ์ Employee ไม่เข้า manager, duplicate ID, enrollmentครั้งเดียว,card/NFC,QRพร้อมกันและหมดอายุ,faceJPEGและภาพไม่มีหน้า
  5. ทดสอบ card session: role,owner,เครื่องเดียว,confirmก่อนcapture,บัตรซ้ำ,ไม่มี event/กลอนตอนcapture,confirmซ้ำไม่เพิ่มcredential,หมดอายุ,ยกเลิก

28 · เมื่อของมาถึง เริ่มทดสอบอะไร

ทดสอบทีละส่วนก่อนเปิดการควบคุมประตูจริง ไม่ถือว่า PCBสั่งแล้วแปลว่าพินตรงหรือไฟพร้อม

  1. ตรวจ BOM/รุ่น MCU/กล้อง/reader/แรงดันและโหมด interface เทียบ schematic
  2. ก่อนจ่ายไฟ ตรวจ short, polarity, fuse, regulator และขา connector; ใช้แหล่งจ่ายที่เหมาะกับวงจร
  3. วัด rail ต่าง ๆ แล้วทดสอบเปิด MCU/Serial ก่อนต่อโหลดกลอน
  4. ทดสอบ cameraReady จริงและ JPEG ชัด; แก้ 0x105 ก่อนทดสอบรู้จำ
  5. ทดสอบ readerReady และ UID จริง แล้วใช้หน้าเว็บผูกกับพนักงานทดสอบที่สร้างใหม่
  6. แตะบัตรคนที่มีสิทธิ์/ไม่มีสิทธิ์/วิธีปิด/นอกเวลา/บัตรrevoke และดูเหตุผลตรงกัน
  7. ทดสอบ faceกับแสงและมุมจริง ไม่ใช้เพียงรูปเดียวสรุปaccuracy
  8. เมื่อซอฟต์แวร์ผ่านแล้วจึงออกแบบ/testการสั่งกลอนและfeedbacksensorแยก พร้อมทางออกที่เหมาะสมก่อนใช้จริง
  9. เก็บผลวัดไฟ/อุณหภูมิ/ความหน่วง/จำนวนใช้ต่อเนื่อง และปรับload testตามจำนวนคนจริง

29 · ขึ้นโฮสติ้งภายหลัง

  7. ทดสอบครบเส้นทางบนปลายทางจริงก่อนนำไปควบคุมประตู
